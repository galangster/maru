# Wren — UI review, 2026-08-29

**Verdict: Blocked. Grade: B‑plus.**

Second full cycle. Scope: the three agent surfaces the first audit never saw — the approval
queue, Settings → Agents (including the one-time credential moment), and the audit timeline —
plus regression spot-checks on the inbox, composer, palette, universal keys and celebrations.
Driven live at `http://localhost:1420/?demo=1` in both themes, at 1440 px and 950 px, with
geometry, colour and focus measured in the page rather than read off screenshots.

**Counts: 2 blocking, 11 should-fix, 8 nits.**

## Why B-plus rather than higher or lower

The craft here is genuinely high and, unusually, it is *argued*. Reduced motion is solved once
by zeroing the tokens the keyframes are written in terms of, which reaches even inline
`style={{animation}}` — that is a better answer than most codebases arrive at. The dark surface
set is designed rather than inverted and every tier I measured lands on DIRECTION §3's ratified
table. The audit table's rhythm is exactly the Aave register §2 asks for, at exactly 44 px. The
security defaults are right: a new agent is created with nothing, and `send` opens on
`{kind: 'domains', domains: []}` rather than on "anyone".

What holds it at B-plus is a coherent cluster of accessibility failures on the surfaces where
trust is actually transacted. Approving mail ejects the keyboard user from the dialog. Two ARIA
patterns announce a keyboard contract that is not implemented. The one-time credential — the
single most irreversible thing in the app — is set in the app's quietest type tier and is
destroyed by one unguarded click. None of these are visible in a screenshot, which is precisely
why they survived to here.

Every fix from UI-REVIEW-2026-08-28 held. One nit regressed (S7 below).

## Blocking

### B1 · Approving or denying drops focus to `<body>` inside the still-open modal

`src/features/agents/approval-queue.tsx:161-198`, with the row removed at `:113-117`.

Measured: focus the first Approve button, click, wait for the 200 ms settle —
`document.activeElement === document.body` and `activeElement.closest('[role=dialog]') === null`,
while the dialog is still open with one request remaining.

The row that owned focus is unmounted by the query invalidation in `settle()`, and nothing
catches it. The skill's first interaction rule is that focus is never lost. A keyboard user who
approves the first of several requests is ejected from the surface they are working in; Tab
restarts from an undefined place and a screen reader loses its position entirely.

It is also silent. Deny is deliberately toastless (`:186-188`, a good decision on its own), and
Approve's confirmation is a purely visual fill-and-glyph swap on a node that is then removed.
The only `aria-live` region in the document is Sonner's, and it is empty. So for assistive
technology, approving mail produces no announcement and no focus anchor.

**Fix.** Before calling `settle()`, move focus deterministically — to the next row's Approve if
one exists, otherwise to the queue's close button — and announce the outcome through a polite
live region ("Sent. 1 request left." / "Denied."). Base UI will not do this for you: the removal
happens outside the primitive's focus-management scope.

### B2 · `role="tablist"` and `role="radiogroup"` declare a keyboard contract neither implements

`src/features/agents/audit-timeline.tsx:81-97` and `:152-169`;
`src/features/agents/agents-settings.tsx:297-325`.

Measured live on the timeline's filter tabs: both tabs report `tabIndex = 0` (no roving
tabindex), `ArrowRight` moves focus nowhere, neither carries `aria-controls`, and there is no
`role="tabpanel"` anywhere in the dialog. The send-scope `role="radio"` pair behaves identically.

Both roles are contracts. A screen reader announces "tab, 1 of 2" and the user presses arrow
keys, which do nothing. Meanwhile every tab is its own Tab stop, so a workspace with five agents
produces six stops where the pattern promises one. Declaring the role and omitting its keyboard
model is worse than using no role, because it actively misinforms.

**Fix — the cheap and correct one.** Delete both role sets. The capability chips sixty lines
above (`agents-settings.tsx:223-253`) already use `role="group"` plus `aria-pressed`, which is
honest, needs no arrow keys, and is the right pattern for a filter that is really a toggle. Use
it in both places.

If the tab semantics are genuinely wanted, the full contract is: roving `tabIndex` (0 on the
active tab, -1 on the rest), `ArrowLeft`/`ArrowRight`/`Home`/`End` handlers, `aria-controls` on
each tab, and `role="tabpanel"` with `tabIndex={0}` on the table wrapper.

## Should fix

### S1 · The credential screen: the one-time secret is the quietest thing on it, and one click destroys it

`src/features/agents/agents-settings.tsx:432-485`. This is the trust-critical screen, so it gets
four separate notes.

**The warning is set in the meta tier.** "Copy it into the agent's config now… you won't see it
again" measures `oklch(0.535 0.004 286)` at 13 px, weight 400 — that is `text-3`, which
DIRECTION §3 reserves for timestamps and counts. It is the quietest type in the app, carrying
the only irreversible consequence in the app. Lift it to `text-ink-2` at minimum; `star` is the
app's own warning hue and spending it once here is justified.

**"Done" is an unguarded destroy.** `:475-481` discards the credential permanently with no
confirmation. `copied` is tracked at `:439` and then never used — it changes the Copy button's
glyph and nothing else. The app already owns `ConfirmPopover` and uses it for the *lesser* case
of discarding a draft. Use it here when `!copied`, or keep Done visually secondary until Copy
has fired.

**The credential is unreachable by keyboard.** It renders as a `<p>` with `user-select: all` and
`tabIndex = -1` (measured) — clickable, not focusable. When `navigator.clipboard.writeText` is
refused, the error toast at `:449` says "Select the credential and copy it by hand", an
instruction a keyboard-only user cannot follow. Render it as a `readOnly` input or textarea, so
it takes focus and ⌘A selects it.

**Nothing announces it.** Creating the agent swaps the form for the credential in place with no
`aria-live`, and focus lands on the Settings dialog root (measured: `DIV#_r_j_`). A screen-reader
user receives no signal that a one-time secret is now on screen and about to be lost.

### S2 · The approvals badge fails AA in the light theme — measured 4.21:1

`src/features/sidebar/sidebar.tsx:388`.

`text-brand` `oklch(0.545 0.185 268)` on `bg-fill-selected` (the accent at 8 %) over `base`.
Composited and sampled through a canvas: foreground `rgb(67, 100, 218)` on an effective
background of `rgb(229, 232, 243)` = **4.21:1**, at **11.5 px / weight 500**. That is body-size
text and needs 4.5. Dark measures **6.84** and is fine.

DIRECTION §3's verified table gives accent-on-`base` as 4.71, which passes — the 8 % wash is
what eats the remaining margin, because the wash is darker than the canvas it sits on. This is
the primary and only entry point to the approval queue, so it is the wrong control to lose
legibility on.

**Fix.** Either drop the wash and put accent ink straight on `base` (4.71), or keep the wash and
render the numeral in `text-ink`, letting the icon carry the accent alone.

### S3 · Expanding one request moves the other request's Approve button 75 px

`src/features/agents/approval-queue.tsx:237-248`, inside a dialog centred by
`src/components/ui/dialog.tsx:61` (`top-1/2 … -translate-y-1/2`).

Measured. Collapsed, the two Approve buttons sit at y = 425.5 and y = 620.5. Expanding
**request 2** moves **request 1's** Approve to y = 350.5 — an instant 75 px jump, with no
animation, on the control that sends mail. Because the card grows from its centre, the shift
runs in both directions: expanding request 1 pushes request 2 down by the same 75 px.

Reading the second request before deciding on the first is the normal way to use this queue, and
it relocates a send button by more than two row heights while the cursor is in flight.

**Fix.** Pin the dialog's vertical position while it is open — a fixed top offset instead of
`top-1/2 -translate-y-1/2` — so the card grows downward only. That removes the shift on the rows
above the one being expanded, which is the dangerous half.

### S4 · The queue's timestamp reads as a time of day, and offers no way to resolve it

`src/features/agents/approval-queue.tsx:208-210`.

`relativeTime` renders anything from today as a clock time. The two live requests displayed
**"00:59"** and **"00:24"**. On the one surface whose entire question is "how long has this been
waiting", that parses as 12:59 AM rather than 59 minutes. The audit timeline hedges the same
function with `title={fullTimestamp(entry.at)}` (`audit-timeline.tsx:189`); the queue has no
`title` at all, so there is no way to disambiguate it.

This also matters because the empty state promises "a request expires on its own after a day"
(`:131-134`) — a claim the user cannot check against the time shown.

**Fix.** Use an elapsed form here ("59m ago"), and add the absolute timestamp as a `title`.

### S5 · The audit timeline renders up to 500 unvirtualized table rows

`src/features/agents/audit-timeline.tsx:109-125`; cap at `src/core/agents/audit.ts:15`
(`AUDIT_READ_CAP = 500`).

About eleven rows are visible in the 560 px scroller. The other ~489 are mounted, each carrying
four `<td>`, an `AgentDot`, an `OutcomeMark` and a `title`. The thread list already solved this
with `@tanstack/react-virtual`; this table does not use it. Capped is not the same as cheap —
500 rows is well past the point where virtualization earns itself.

**Fix.** Virtualize with the same primitive the thread list uses, or page the log.

### S6 · The capability chip's accessible name omits the agent — the opposite of what its own comment claims

`src/features/agents/agents-settings.tsx:231-233`.

The comment reads "Two identical words down a list of agents; the label says whose." The measured
accessible name is `"Read — Search the mailbox and open threads."` — the agent's name is not in
it. With two agents, a screen reader encounters eight buttons carrying four names, twice, with
nothing distinguishing which agent each belongs to. This is a permissions control, so "which
agent" is the whole question.

**Fix.** `aria-label={`${label} for ${agentName} — ${help}`}`, threading the name into
`CapabilityToggles`.

### S7 · `title` duplicates the accessible name — UI-REVIEW-2026-08-28 N7, reintroduced

`src/features/agents/agents-settings.tsx:232-233`. The same button carries
`aria-label="Read — Search the mailbox and open threads."` and
`title="Search the mailbox and open threads."`.

**This is the one regression in this cycle.** N7 flagged exactly this pattern on
`wren-controls.tsx:114-115` and it was fixed there; the new code reintroduces it. Screen readers
may announce both strings, `title` is mouse-only and cannot be styled, and the help text is
already rendered as visible prose at `:255-259`.

**Fix.** Drop the `title`.

### S8 · The credential cards are stroked, in a file that argues against strokes

`src/features/agents/agents-settings.tsx:454` and `:173` use `border-hairline border` with no
fill — measured `1px solid oklch(0.923 0.003 286)`, `background: rgba(0, 0, 0, 0)`,
`box-shadow: none`.

`AgentCard` at `:111` uses `bg-sunken` and carries the comment "A well, not a card with a stroke:
depth by fill (DIRECTION §1)". DIRECTION §1 says depth comes from fill steps and soft ambient
shadow, "never from strokes". Two card treatments in one file, one of them contradicting the
argument the other one makes 340 lines earlier.

**Fix.** `bg-sunken`, no border, matching the sibling.

### S9 · The trust-critical surface has no keyboard path

The approval queue's only entry point is `ApprovalsBadge`
(`src/features/sidebar/sidebar.tsx:370-402`), a status-bar button.

Verified: searching "appro" in the command palette returns "Nothing matches"; there is no
binding in `src/features/keyboard/keymap.ts`; nothing appears in the "?" sheet. The audit log is
reachable only from inside the queue, or by scrolling to the bottom of Settings → Agents.

In an app that ships a full command palette and a printed shortcut sheet, the one surface that
gates outbound mail is mouse-only. The badge's "absent at zero" decision (`:374`, and well
argued in its comment) compounds it: when the queue is empty there is no way to open it at all.

**Fix.** Add both surfaces to the palette's Actions group, and give the queue a binding in
`keymap.ts`.

### S10 · A permission that is ON is visually quieter than one that is OFF

`src/features/agents/agents-settings.tsx:246`.

Measured: granted = `bg-fill-selected`, `oklch(0.545 0.185 268 / 0.08)`; not granted =
`bg-surface`, `oklch(1 0 0)`. Both sit on a `bg-sunken` card, so the *ungranted* chip is pure
white and reads as the brighter, raised one. The icon is `text-ink-3` in both states, so the
check-versus-plus glyph carries the distinction at the muted tier.

For a permissions control, the consequential state should be the louder one.

*(Checked and clear while here: font-weight is 500 in both states — measured 0.00 px width delta
and 0.00 px neighbour displacement on toggle. No reflow. The `font-medium` on the active branch
is a no-op against the inherited UI weight.)*

### S11 · The settings dialog's fixed 440 px height now overflows badly

`src/features/settings/settings-dialog.tsx`. Measured on the Agents section: content
`scrollHeight` 708 in a `clientHeight` of 392. "New agent" and "Open the audit log" both sit
below the fold behind nothing but a `scroll-fade`.

UI-REVIEW-2026-08-28 N4 raised the same fixed height from the other direction — Appearance was
nearly empty. One section is now half air and another is 1.8× over. A fixed height cannot serve
both.

**Fix.** `min-h` plus `max-h` instead of a fixed height.

## Nits

- **N1 · The same control has two shapes.** "Open the audit log"
  (`agents-settings.tsx:69-75`) is `rounded-md` with no hover fill; the identical "Audit log" in
  the queue header (`approval-queue.tsx:90-96`) is `rounded-full` with one. DIRECTION §6 makes
  buttons pills. The focus ring differs too, since it follows the radius.
- **N2 · The timeline draws the empty space the queue refused to.** `audit-timeline.tsx:46` is
  `h-[560px]` fixed, while `approval-queue.tsx:63` caps with `max-h-[640px]` and shrinks — its
  comment explicitly rejects drawing "a half-metre of nothing", which is what the timeline's
  empty state does.
- **N3 · An approved request keeps "Waiting" in the Outcome column forever.** With the queue
  empty, the log still shows two rows outcome-marked `Waiting`. Append-only is a defensible
  model; the column header labelled **Outcome** is what makes it read as stale.
- **N4 · Non-concentric radii.** `agents-settings.tsx:454` is `rounded-md` (12) with `p-4` (16)
  wrapping a `rounded-sm` (8) well; DIRECTION §6's inner = outer − inset gives 0. Same shape at
  `:173`/`:179`.
- **N5 · Six settings tiles, five licensed.** DIRECTION §3 permits settings-section tiles as the
  one chrome exception at "five fixed positions". There are now six sections.
- **N6 · The credential is set in a proportional face.** Measured: DM Sans, 13 px, with
  `word-break: break-all`, so `O`/`0`, `l`/`I` and `5`/`S` are ambiguous in the one string in
  the app that must be transcribed exactly — and it breaks mid-token, leaving a lone `4` on the
  second line. DIRECTION §4 declares only two families, so adding a mono face is an owner
  decision rather than a defect. Raising it because this is the string that needs one.
- **N7 · At 950 px the status bar truncates "Demo data" to "D"** rather than dropping the label.
- **N8 · Two unordered writes to the same grant.** `SendScopeEditor` commits domains on `blur`
  only (`agents-settings.tsx:336`). Switching the radio to "Anyone" fires `commit()` from the
  blur and `setScope('all')` from the click as two async `gateway.grant` calls against the same
  key, with no ordering guarantee.

## Note on method

Real Tab traversal could not be verified through the in-app browser pane: trusted key events
reach JavaScript listeners (⌘K, `e`, `j` and ⌘Z all fired, with `isTrusted: true`), but native
default actions do not run — a dispatched `Tab` left `document.activeElement` unmoved with
`defaultPrevented: false`. Focus order was therefore verified programmatically, by enumerating
the focusable set in DOM order and comparing it against measured geometry. The focus-loss finding
in B1 is a direct read of `document.activeElement` after a real click and is unaffected by this
limitation.
