# Wren — UI review, 2026-08-28

**Verdict: Blocked. Grade: B+.**

Wren is built to a standard most products never reach. `tokens.css` is a real design
system, not a palette dump: the OKLCH ramps carry verified contrast, the motion tokens are
three durations and two easings with the reduced-motion case solved once by zeroing the two
quantities every keyframe is written in terms of, and `surfaces.css` correctly hands unmount
authority to Base UI instead of fighting it with `AnimatePresence`. The icon seam is a single
file. The list is virtualized. `tabular-nums` is global. Every interactive element I traversed
had a visible focus ring. The code comments argue their own decisions and several of them
record a defect that was found and fixed. That is the top decile of front-end craft.

It is Blocked anyway, on three findings that break the accessibility and interaction floor,
not on taste. The thread list puts **79 invisible tab stops** between the list header and the
reading pane; its `role="listbox"` is never focusable and never sets `aria-activedescendant`,
so an assistive-technology user cannot browse mail at all; and `⌘K` opens the command palette
**on top of** an already-open dialog, stacking two modals and two glass layers, which Wren's
own DIRECTION §7 rule 1 calls "a bug" in those words. Below the blockers sits a set of
measurable alignment and consistency defects that DIRECTION §1 ("Columns line up across every
row of a list, always") and §8 (the 16/18/20 icon grid) already forbid — a ragged timestamp
column in search, a 46.9 px label drift inside one column of the shortcut sheet, and two
toolbars sitting side by side at the same y with different icon sizes. None of that is hard to
fix. All of it is the difference between a B+ and the A this system is otherwise built for.

**Icons are excluded from the grade as an icon set.** They are lucide-react on an interim
basis with the Anron swap pending, and `src/components/ui/icon.tsx` is a correctly built seam
that makes the swap a one-file change. Icon *sizing, alignment and stroke consistency* are
graded, and are where findings 11, 12 and 19 come from.

Measurements below were taken live at 1440×900, 960×800 and 940×760 against
`http://localhost:1420/?demo=1` in both themes, via `getBoundingClientRect` and
`getComputedStyle` rather than read off screenshots.

## Blocking

### B1 · The thread list has 79 phantom tab stops

`src/features/list/thread-row.tsx:168-208` (`QuickActions`), rendered per row from
`src/features/list/thread-list.tsx:232`.

Every rendered row mounts a four-button hover cluster that is `opacity-0` but fully in the tab
order. Measured on the inbox at 1440×900:

- `document.querySelectorAll(<tabbable>)` → **96** elements.
- Tab index 12 is the list's Refresh button. Tab index **93** is the reading pane's Reply
  button. Between them: 79 stops, every one of them an invisible per-row action.
- 18 of the 19 rendered rows contribute 4 buttons each.

A keyboard user who Tabs off the list header must press Tab ~81 more times to reach the
reading pane. There is no roving-tabindex, no `tabindex="-1"` on the inactive clusters, and no
skip affordance.

**Why it hurts.** This is not slow, it is unusable — the standard non-mouse path through the
app's primary surface is broken. It also makes the focus ring appear on rows the user is not
looking at, because `focus-within` reveals each cluster as focus lands in it.

**Fix.** Give the quick-action buttons `tabIndex={-1}` and expose them only for the row that is
currently selected (`selected ? 0 : -1`), so exactly one cluster is reachable — the roving
tabindex pattern. The row's actions already have full keyboard equivalents (`e`, `#`, `s`, `u`
in `src/features/keyboard/keymap.ts:56-59`), so the cluster is a mouse convenience and should
not own tab stops at all. See `better-accessibility` (keyboard navigation, tab order) and
`touch-and-accessibility`.

### B2 · `⌘K` stacks a second modal on top of an open dialog

`src/features/keyboard/use-shortcuts.ts:127-131`, which runs **before** the guard at
`:134` (`if (anyDialogOpen()) return`).

Reproduced: open the shortcut sheet (`?`), press `⌘K`. Measured state afterwards:

```
dialogCount: 2
  "Keyboard shortcuts"  520×…  at (460, 253)  z-index 50
  "Command palette"     600×…  at (420, 144)  z-index 50
glassLayers: 2      scrimLayers: 2
```

Two `role="dialog"` nodes, both claiming modality, both at `z-index: 50`, overlapping
rectangles, two scrims stacked. The palette's `glass-strong` and the sheet's `glass` are both
live, so the palette's content ghosts through the sheet and neither surface is legible.

**Why it hurts.** Three separate failures at once. (1) Focus containment between two
simultaneous modals is undefined — the palette input holds focus while the sheet paints on
top. (2) DIRECTION §7 rule 1 sets the glass budget at "a palette over a scrim… a third is a
bug"; this is two glass surfaces plus two scrims. (3) The composer already solves this
correctly — `src/features/compose/composer.tsx:159` drops its own blur via `glassOff` when
`useAnyDialogOpen()` is true — so the app knows the rule and only the palette breaks it.

**Fix.** In the `⌘K` branch, close whatever dialog is open before opening the palette:

```ts
const s = useSurfaces.getState()
if (s.settings || s.shortcuts || s.onboarding) {
  useSurfaces.setState({ settings: null, shortcuts: false, onboarding: false })
}
s.setPalette(!s.palette)
```

The intent recorded at `use-shortcuts.ts:9-10` — "a palette you cannot reach from a text field
is not a palette" — is preserved; only the stacking goes. See `animations` (surface layering)
and DIRECTION §7.

### B3 · The listbox is unreachable and its options contain focusable children

`src/features/list/thread-list.tsx:215-220` and `src/features/list/thread-row.tsx:63-74`.

Measured on the live list:

```
listboxTabIndex: null          listboxActiveDesc: null
optionsWithButtons: 18
```

The `role="listbox"` container is not focusable and never sets `aria-activedescendant`, so no
option is ever the focused element — `aria-selected` moves but nothing announces. Separately,
18 of 19 `role="option"` nodes contain `<button>` descendants (the star at `thread-row.tsx:136`
and the four quick actions). ARIA forbids focusable content inside `option`; screen readers
flatten an option to its text label, so those buttons are announced inconsistently or not at
all.

**Why it hurts.** j/k navigation works for a sighted mouse-and-keyboard user and the visual
selection is correct, which is exactly why this was missed. For anyone on a screen reader the
mail list — the product's primary surface — has no navigable structure.

**Fix.** Two changes. Put `tabIndex={0}` on the listbox and drive
`aria-activedescendant={<selected row id>}`, giving each `ThreadRow` a stable `id`; the j/k
handlers in `use-shortcuts.ts:66-75` already compute the right target. Then take the buttons
out of the options — B1's roving tabindex plus `aria-hidden` on the non-active clusters
resolves both findings with one edit. See `better-accessibility` (ARIA, custom widgets).

## Should fix

### S1 · Motion on two 100-plus-times-a-day keyboard actions

`src/features/shell/surfaces.css:45-47` and `src/features/reading/reading-pane.tsx:97-103`.

- The palette enters with `animation: wren-surface-in var(--wren-dur-base) var(--wren-ease-spring)`
  — 200 ms on `cubic-bezier(0.34, 1.4, 0.64, 1)`, a curve that overshoots past 1.
- The reading pane crossfades on **every** thread change:
  `crossfadePreset` → `{ opacity 0→1, y 4→0 }` at `DUR.base` (200 ms), keyed on `thread.key`,
  so every `j` and every `k` replays it.

**Why it hurts.** Both are flag-on-sight items: animation on a command-palette toggle, and
animation on a 100+/day action. A triage user pressing `j` down a mailbox pays 200 ms of fade
per row; the content is legible before the fade completes, so the motion reads as lag rather
than as feedback. The spring overshoot on a surface summoned by muscle memory is decoration on
the highest-frequency element in the app.

**Fix.** Palette: `--wren-dur-fast` (120 ms) on `--wren-ease-out`, or opacity only. Reading
pane: drop the `y: 4` step and shorten to `DUR.fast`, or cut the animation entirely when the
selection changed from the keyboard. DIRECTION §9's own table assigns `--wren-dur-slow` here,
which is the wrong direction — the doc should move with the code. See `animations`
(frequency-appropriate motion).

### S2 · The hover cluster covers the timestamp and the end of the subject

`src/features/list/thread-row.tsx:179`.

Measured at 1440×900, list pane 400.28 px wide:

- Quick-action cluster: x **501.45 → 637.45** (136 px wide, `right-3`).
- Timestamp column: x **569.45 → 633.45** (`w-16`, `thread-row.tsx:112`).

The cluster sits entirely on top of the timestamp and over the tail of the snippet. Confirmed
visually in both themes: hovering any row hides when the mail arrived.

**Why it hurts.** The timestamp is the row's right-hand anchor and one of the two things a
user scans for. Hiding it on hover means it disappears exactly when the cursor is on the row
being read. It also puts four click targets under a pointer that was aiming at the row — my
first click at the row's right side fired a quick action instead of opening the thread.

**Fix.** Reserve the cluster's width in the row and let it slide into a gutter rather than
over content, or shift the cluster to sit after the timestamp with the row's flex line
reflowing. Keeping the timestamp visible is the constraint. See `better-layout`.

### S3 · Search-result timestamps are ragged — the exact defect the list forbids

`src/features/search/thread-result.tsx:50`.

```tsx
<span className="text-ink-3 shrink-0 text-xs tabular-nums">
```

No fixed width. `thread-row.tsx:112` uses `w-16` and its own comment says why:

> a shrink-to-fit column would leave the left edge of the timestamps ragged down the list,
> which is the one thing DIRECTION §1 says a column may never do.

Measured across two live search results: `"Yesterday"` and `"Sun"` (21.5 px) start at
different x. The rule was written down, then not applied to the second row component.

**Fix.** Add `w-16 text-right` to match `thread-row.tsx:112`. One-line change.

### S4 · The 152 px sender column starves the subject on one-line rows

`src/features/search/thread-result.tsx:44-49`.

Measured on a live search result in a 400 px pane:

| Part | x | width |
|---|---|---|
| avatar | 265 | 32 |
| sender `"Maya, Dev"` | 309 | **152** (needs ~55) |
| subject `"Design review: settings…"` | 473 | **126.5** |
| time `"Sun"` | 611.5 | 21.5 |

The fixed column is correct for the two-line list row, where the subject lives on line 2 at
full width. On a one-line result the sender and the subject compete for the same line, so
~97 px of dead space inside the sender column costs the subject two-thirds of its room and it
truncates at 14 characters.

**Fix.** Cap the sender with `max-w-(--wren-list-sender-w)` and let it shrink, or drop to a
`min-w` on the same token. Alignment across result rows is preserved by the avatar and the
fixed time column from S3.

### S5 · Shortcut-sheet labels do not line up inside a column

`src/features/keyboard/shortcuts-overlay.tsx:46-53`.

The keycap cluster is `shrink-0` with no width, so the label x is a function of the keycap
text. Measured label x within each column:

- **Move**: 513, 513, 513, **559.9** (`⌘1 … ⌘4`, keycap 66.9 px) — 46.9 px drift.
- **Write**: 513, 513, 513, 513, **524.1** (`⌘↵`).
- **Find**: **771.3** (`⌘K`), 764, 764, **771.5** (`esc`).

**Why it hurts.** This is the one surface whose entire job is to be scanned as a table, and it
is the one place DIRECTION §1's column rule is broken outright.

**Fix.** `w-18` (72 px, on the 4 px grid, clears the 66.9 px worst case) on the keycap span at
`:46`, with `justify-end` so the caps sit against the labels.

### S6 · Message bodies shift the layout on every open

`src/features/reading/message-body.tsx:90` — `const [height, setHeight] = useState(120)`.

Every iframe mounts at 120 px and then jumps to its measured height once the `ResizeObserver`
fires. For a long message that is a several-hundred-pixel shift after paint, and the reply
tiles below it move with it.

**Fix.** Reserve space from data — `message.bodyText?.length` or a stored last-known height
per message id gives a much closer first guess than a constant — and animate nothing. At
minimum, hold the previous message's height rather than resetting to 120. See `ui-polish`
(layout stability) and `performance`.

### S7 · All three pane boundaries land on fractional pixels

`src/features/shell/app-shell.tsx:62-79` passes pixel measures to `react-resizable-panels`,
which stores sizes as percentages. Measured at 1440×900:

| Pane | token | actual |
|---|---|---|
| sidebar | 248 | **248.172** |
| list | 400 | **400.281** |
| reading | — | **789.547** |

so the pane edges sit at x = 249.172 and x = 650.453.

**Why it hurts.** DIRECTION §6 is emphatic that a hairline is "always exactly 1px… Never
0.5px — Windows WebView2 at 100% DPI rounds it to 0 or renders it blurry." The pane separators
are real `border-inline-end`s on a fractional boundary, which produces precisely that: a
hairline straddling two device pixels at half alpha each. It also puts every column inside the
list on a fractional origin, so text rasterizes at sub-pixel offsets that differ pane to pane.

**Fix.** Round the resolved panel widths to whole pixels (the library exposes `onResize` with
`size.inPixels` — snap and write back), or set the sidebar and list as fixed-width flex
siblings and let only the reading pane flex. The tokens are already correct; only the delivery
is lossy.

### S8 · Two toolbars at the same y carry different icon sizes

DIRECTION §8: "16 inline with text and meta, **18 default for toolbars and menus**, 20 for
sidebar nav and primary actions."

Measured `svg` widths across the chrome:

| Surface | file:line | size | spec |
|---|---|---|---|
| sidebar nav | `sidebar.tsx:144` | 20 | ✅ 20 |
| reading toolbar | `reading-pane.tsx:78` (default) | **18** | ✅ 18 |
| list toolbar (Search, Refresh) | `thread-list.tsx:153`, `:254` | **16** | ❌ should be 18 |
| titlebar (Collapse sidebar) | `titlebar.tsx` | **16** | ❌ should be 18 |
| sidebar footer (Settings, theme) | `sidebar.tsx` | **16** | ❌ should be 18 |
| composer toolbar | `composer.tsx:318`, `body-editor.tsx` | **16** | ❌ should be 18 |

The list header and the reading header are both `h-(--wren-toolbar-h)` (52 px), sit at the
same y, and are separated by a 1 px rule — so the 16 vs 18 mismatch is visible as a direct
side-by-side comparison, which is the worst case for an icon-size inconsistency.

**Fix.** Drop the `size={16}` overrides in the four toolbar call sites; `IconButton` already
defaults to 18.

### S9 · Two icons render off the 16/18/20 grid, at the wrong stroke weight

- `src/features/compose/chip-input.tsx:78` — `<Icon name="close" size={16} className="size-3" />`
  → renders at **12 px**.
- `src/features/compose/composer.tsx:298` — `<Icon name="close" size={16} className="size-3.5" />`
  → renders at **14 px**.

`Icon` sets `strokeWidth` from the `size` prop (`icon.tsx:132`), so both compute 1.75 for a
16 px glyph and then scale the SVG down via CSS. `vector-effect: non-scaling-stroke` is applied
(`icon.tsx:136`), which means the stroke does **not** scale with the box — it stays at 1.75 on
a 12 px glyph, so it reads ~33% heavier than every other icon in the app.

**Fix.** Remove the `className` size overrides and pass a grid size, or add 12/14 to `IconSize`
with their own stroke widths if the small chips genuinely need them. DIRECTION §8 says the grid
is 16/18/20, so removing the overrides is the intended answer.

### S10 · Two interactive targets under 24×24

- `src/features/compose/chip-input.tsx:76` — `size-4` → **16×16** (recipient chip remove).
- `src/features/compose/composer.tsx:296` — `size-5` → **20×20** (attachment remove).

Both are below WCAG 2.2 SC 2.5.8's 24×24 minimum, and well below the app's own `--wren-hit`
of 32 px. Every other control I measured in the composer is exactly 32×32, so these two are
outliers rather than a policy.

**Fix.** The pattern is already in the codebase — `thread-row.tsx:146` keeps a 16 px glyph and
restores a 32 px hit box with `after:absolute after:-inset-2`. Apply the same to both. See
`touch-and-accessibility`.

*Context on the 44 px floor:* Wren is a Tauri desktop app with no touch target, so the 44×44
mobile figure does not bind. 24×24 (WCAG 2.2) and the project's own 32 px `--wren-hit` do, and
these two miss both.

### S11 · No `font-synthesis: none`

Absent from `src/styles/tokens.css` and `src/index.css` (grep: zero occurrences).

DIRECTION §4 ends with "Never fake a weight." Nothing enforces it. DM Sans is loaded at 400 and
500 only (`tokens.css:45-58`); any `font-semibold` or `font-bold` on body copy — including
inside a sanitized email body, which is arbitrary third-party markup — gets a synthesized
faux-bold from the browser.

**Fix.** `font-synthesis: none` in the `@layer base` body rule at `tokens.css:455`, and in
`buildSrcdoc`'s stylesheet at `src/lib/sanitize.ts:110` so mail bodies fail visibly rather than
faking. See `typography`.

### S12 · The Tooltip component is built and used nowhere

`src/components/ui/tooltip.tsx` exists, is styled, and has **zero** imports outside itself.
Every tooltip in the app is a native `title` attribute:
`wren-controls.tsx:114` (`IconButton`, so every icon button in the product),
`sidebar.tsx:131` (the collapsed rail's only labels),
`reading-pane.tsx:185` (the R/A/F shortcut hints),
`composer.tsx:336` (`Send (⌘↵)`), `thread-row.tsx:152`.

**Why it hurts.** `title` has a ~1 s OS-controlled delay, cannot be styled, never appears on
keyboard focus, and is unreliable across screen readers. In the collapsed 64 px rail it is the
*only* way to learn what an icon means, and a keyboard user tabbing the rail sees nothing. The
R/A/F shortcut hints in the reply bar are discoverable by hover alone.

**Fix.** Wrap `IconButton` in the existing `Tooltip` and drop the `title` prop; keep
`aria-label` as the accessible name. Move the reply-bar hints to visible `Keycap`s — the tiles
are 40 px tall and have the room.

### S13 · The composer's glass is too transparent for a writing surface

`src/features/compose/composer.tsx:205` uses `.glass` — tint `oklch(1 0 0 / 0.72)` measured
live, `blur(20px) saturate(1.8)`.

Docked bottom-right at 560×440 over the reading pane, the mail behind reads through the From,
To and Subject rows clearly enough to compete with what is being typed.

**Why it hurts.** DIRECTION §7 does license the composer sheet as glass, so this is not a rule
break — but §1's principle ("Put glass behind text that must be read" is on the refuses list)
applies to text the user is *writing* just as much as text they are reading. The settings
dialog already made exactly this call and moved to `glass-strong`, for exactly this reason
(`settings-dialog.tsx:4-8`: "at the lighter tint the empty right-hand column let the reading
pane's copy read straight through it").

**Fix.** Move the composer to `.glass-strong` (0.82 tint), matching the precedent set in
settings. See `surfaces`.

## Nits

Optional. None of these would hold a release on their own.

- **N1 · Twelve unused shadcn files, and all four `transition: all` live in them.**
  `button.tsx:7`, `badge.tsx:8`, `switch.tsx:19`, `tabs.tsx:61` each carry `transition-all` —
  and all four files have **zero** imports outside `components/ui/`. Also unused:
  `dropdown-menu`, `tooltip` (see S12), `sheet`, `card`, `avatar`, `input-group`,
  `scroll-area`, `command`. Nothing renders them, so no unbounded property animation ships;
  they are dead scaffolding that will trip the next reviewer exactly as it tripped this one.
  Delete them, or leave a note in `components.json`. The live code's z-index discipline is
  genuinely good — 10 (titlebar) / 40 (composer) / 50 (dialogs), with `isolation: isolate` on
  the portal roots.

- **N2 · Non-concentric nested radii.** `message-card.tsx:62` is `rounded-lg` (16) with `p-4`
  (16), so DIRECTION §6's `inner = outer − padding` gives 0 — but the body iframe is
  `rounded-md` (12) at `message-body.tsx:166`. Same shape in settings: a 28 px dialog with
  `p-2` nav padding and `rounded-md` (12) items, where 20 is the concentric answer. The
  Appearance segmented control gets it right (`settings-dialog.tsx:142,157`: `rounded-md` outer,
  `p-1`, `rounded-sm` inner = 12 − 4 = 8) — that is the pattern to copy.

- **N3 · Collapsed sidebar account rows are a bare 6 px dot.** At 960 px the rail collapses
  correctly to 64 px, but `sidebar.tsx:145-146` falls through to `<AccountDot>` when a row has
  no `icon`, so two account entries render as naked 6 px dots floating in 40×36 buttons. They
  are correctly labelled (`title` + `aria-label`), but visually they read as a rendering fault.
  Use the account-tinted `AccountAvatar` or an inbox glyph in the account colour.

- **N4 · The fixed 440 px settings dialog leaves Appearance nearly empty.** The fixed height is
  well argued (`settings-dialog.tsx:67-69`) and right for stability, but Appearance holds one
  36 px segmented control above ~330 px of void. Top-aligning the content and letting the void
  sit below the fold of a shorter section, or pairing the theme control with the About block,
  would read as finished rather than as a section that failed to load.

- **N5 · `::-webkit-scrollbar` is global.** `index.css:133-143` uses bare selectors while the
  comment above claims the styling is for the two scrolling panes. Harmless in practice —
  `body` is `overflow: hidden` and the panes are the only scrollers — but the comment and the
  selector disagree, and `ui-polish` asks for scoped scrollbar styling.

- **N6 · Spec drift worth reconciling in DIRECTION.** The palette enters at `--wren-dur-base`
  (200 ms) where §9's table assigns `--wren-dur-slow`; `--wren-pane-px` (16 px) is listed in
  §5 but absent from `tokens.css`; and `--wren-space-*` was deliberately dropped in favour of
  Tailwind's scale, documented at `tokens.css:282-283` but not in §5. The code is right in each
  case — the document should follow it.

- **N7 · `title` duplicates `aria-label` on every `IconButton`** (`wren-controls.tsx:114-115`).
  Some screen readers announce both. Resolved by S12.

- **N8 · Skeleton geometry does not match the loaded row.** `thread-list.tsx:310` uses `gap-2`
  where the real row (`thread-row.tsx:87`) uses `gap-1`, and two `h-3` bars where the row has a
  20 px and an 18 px line. Row height matches at 68 px so nothing shifts; the shape just is not
  the content's shape.

- **N9 · `<li>` between `role="listbox"` and `role="option"`** in the search results
  (`thread-list.tsx:185-188`). The intervening `listitem` role breaks the required
  owned-element relationship. Add `role="presentation"` to the `li`.

- **N10 · The message-body iframe is a dead tab stop.** `message-body.tsx:159` is focusable by
  default, has no focus indicator, and — because keydown events in a same-origin iframe do not
  reach the parent `window` — **every shortcut in `use-shortcuts.ts` is inert while focus is
  inside it.** Tab into a message body and `j`, `k`, `e` and `⌘K` all stop working with no
  visible reason. `tabIndex={-1}` on the iframe fixes both halves.

- **N11 · No `@media (hover: hover)` gating** on the row cluster or any hover state (grep: zero
  occurrences). Correct to ignore for a desktop-only Tauri target; noting it so the decision is
  recorded rather than rediscovered.

## Checked and clean

Stated explicitly so the next reviewer does not re-derive them.

- **`prefers-reduced-motion`** — handled once, elegantly, at `tokens.css:580-601`, by zeroing
  `--wren-lift` / `--wren-scale-in` / `--wren-scale-out` / `--wren-pop` so every keyframe
  degrades to the 120 ms opacity crossfade DIRECTION §9 asks for, with a written justification
  for not collapsing durations to 1 ms. `lib/motion.ts` mirrors it for the motion/react side
  with a third `off` mode for deterministic captures. This is the best implementation of this
  rule I have reviewed.
- **Only `opacity` and `transform` animate.** No layout-property animation anywhere; no
  `backdrop-filter` animation, per DIRECTION §7 rule 3.
- **`ease-in` appears on exits only** (`surfaces.css:40,49,59`), which is correct; it is never
  used on an entrance or an interaction.
- **Virtualization** — `@tanstack/react-virtual` on the thread list with `overscan: 8` and
  stable `getItemKey` (`thread-list.tsx:76-82`). Search results cap at the query; palette hits
  slice to 8.
- **`tabular-nums`** — global at `tokens.css:462`, and re-asserted at every changing figure
  (timestamps, counts, version, byte sizes).
- **No font-weight change on hover or selection.** Unread is a weight change *by state*, not by
  interaction, which is the licensed case.
- **Focus-visible** — a 3 px `ring-ring/50` on every interactive element I traversed by real
  Tab, including the revealed hover clusters. `outline-none` is always paired with a ring
  replacement; I found no bare `outline: none`.
- **Inputs at 14 px** (`text-base`) — the ≥16 px rule exists to stop iOS Safari zooming on
  focus. Wren is Tauri/WebView2/WKWebView on desktop with no iOS target, so it does not bind.
  Recorded as checked, not as a finding.
- **`::selection`** defined (`tokens.css:481`); **`text-wrap`** applied at 13 call sites
  (`text-balance` on headings, `text-pretty` on prose); **empty states** are designed, with the
  title-plus-subtitle shape DIRECTION §2 takes from Family, and a CSS-only cloud mark that needs
  no asset.
- **Contrast** — the ramps in `tokens.css` match DIRECTION §3's computed table; every text tier
  clears AA on every surface it is permitted to sit on, in both themes.
- **Responsive** — the sidebar collapses to the 64 px rail cleanly at 960 px and 940 px, and the
  row snippet drops out below 380 px of list via a container query
  (`thread-row.tsx:130`) rather than a viewport breakpoint. Correct instinct, correctly built.
